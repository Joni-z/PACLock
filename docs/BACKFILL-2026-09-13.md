## Operation

The old packed script waits for its original four children, then exits. Simply
adding an overlapping step would lose new work when those original children exit.
Each controller therefore stops only the original batch **shell**, with PID and
process-start identity checks, while its existing training children keep running.
New training executes inside `srun --jobid=... --overlap` on the allocation's CPUs
and idle GPUs. A node-local process check reads only HIP GPU selectors from owned
Python processes. An atomic shared-filesystem rename claims each configuration
once; no two workers can take the same item. Each launch checks the source YAML's
SHA256 and existing result, and uses an independent MIOpen cache.

Controllers resume the batch shell after draining. A separately launched SSH
watchdog also resumes it if the controller dies or its heartbeat stalls. This
keeps a failed srun step from leaving the allocation shell stopped indefinitely.
A two-second live hold/resume probe on 416457 confirmed that the two original
training processes remained runnable and the shell resumed. Concurrent queue
claim checks verified unique claims and remaining-walltime admission.

## Training budget limitation

Backfilled runs inherit the **remaining** walltime of their host allocation. The
runtime YAML sets `max_hours = min(original_max_hours, remaining_hours - 1)` so
training can evaluate and write results before Slurm terminates the allocation.
Initial caps ranged from about 9.6 to 22.2 hours. Epochs, steps, optimizer, seed,
data, and early-stopping settings remain those of the original configuration.
`backfill` metadata records the original and effective caps in each runtime YAML.

These caps differ between runs. A `stopped_by=time_budget` result is an incomplete
schedule and must not be treated as a completed, budget-matched final comparison
or used to eliminate a model. This dispatcher does not implement checkpoint
resume. Inspect budget-stopped runs before any subsequent scientific comparison.

`squeue` shows the original 17 allocations, not 31 new jobs; the remaining five
configurations initially waited in this filesystem queue, not in Slurm. The
directory contains `migration.json`, `bootstrap.json`, `activation.json`, the
first `live-verification.json`, per-allocation metadata, per-node heartbeat files,
and per-run logs and runtime YAMLs. Configuration records move through
`pending/`, `running/`, and `done/` or `failed/`. Results retain their original
`runs/<name>/seed<seed>/` locations; factorized run directories link to the main
repository's results tree.

To stop a controller, send SIGTERM to its recorded PID on its recorded node. It
terminates its added children and resumes the original batch shell. Do not cancel
the containing Slurm allocation unless all of its original and added work is
intended to stop. A killed controller can leave stale `running/` records: check
the actual node PID and result before retrying anything. Never blindly move all
records back to pending; that could duplicate still-running experiments.

If all usable allocations drain before pending entries are admitted, inspect the
remaining entries and repack them into ordinary four-config Slurm submissions.
Do not blindly resubmit the cancelled source packs, since most of their entries
are already running or complete. Other users' allocations and B2/Torch were not
modified by this migration.
